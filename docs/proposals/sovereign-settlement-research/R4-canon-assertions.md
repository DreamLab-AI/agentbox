# R4 — Canon Register: Prior Asserted Design Choices on RGB/DLC/402/Lightning/Wallets/Ledgers

Scope note up front, honestly stated: the financial-substrate canon is **concentrated
in a small, tightly cross-referenced cluster of ADRs/PRDs** spanning `project/docs`
(VisionClaw side) and `project/agentbox/docs` (agentbox side), plus two explanatory
docs and one README assertion in `solid-pod-rs`. It is **archive-status** (all six
core documents live under `docs/archive/adr` or `docs/archive/prd` on the VisionClaw
side, or the agentbox equivalent — i.e. **superseded/historical per the repo's own
"archive is rationale only, never authority" rule**, EXCEPT that ADR-124/ADR-128 are
marked `Status: Implemented`/`Accepted build-out` and economy-loop.md +
payments-and-web-ledger.md are **living developer docs describing code that exists
today**). None of the eight VisionClaw living governing docs (BASELINE-architecture,
IDENTITY-authority-chain, DATA-authority-erasure, PROTOCOL-registry,
IDENTIFIER-taxonomy, SECURITY-profiles, XR-client, TODO-unified, KNOWN_ISSUES,
MIGRATION-plan) mention RGB/402/Lightning/webledger/blocktrail/gitmark at all — a
grep of all ten for the combined regex returns only unrelated hits on the word
"token" (session/auth tokens). **This is itself a finding: the financial substrate
has no living-governing-doc anchor on the VisionClaw side; its only "living" anchors
are two solid-pod-rs `docs/explanation/*.md` files and one agentbox
`docs/developer/economy-loop.md`.**

## Register

Legend for **built?**: `LIVE` = code cited exists and is routed/tested; `SCAFFOLD` =
compiles, wired partially; `PLANNED` = named, zero code; `HARD-REFUSED` = code
explicitly forbidden until a gate opens.

## Contradictions and tensions

1. **"RGB deferred last, optional" vs. a PRD proposing it now.** ADR-124 §2.2, §9 and ADR-128 §6 (P3) are unambiguous and repeated across two documents: RGB is explicitly the **last**, **optional**, **layer-rewrite** rung of a four-rung ladder, gated behind an independently-audited DLC/adaptor-signature engine (L2) that does not exist. **A PRD that elevates RGB (via sidestr) to an earlier or primary position must explicitly say it is re-sequencing ADR-124/ADR-128, cite them, and either supersede or amend them** — silently introducing RGB without acknowledging this prior sequencing decision would be a doc-drift violation of the estate's own "living doc + ADR ledger" discipline (`project/CLAUDE.md` "Architecture ground truth").

2. **`k256`-only / zero-rust-bitcoin-dep posture vs. `rgb-core`/AluVM.** ADR-124 §2.2 states plainly that `rgb-core` "conflicts with our `k256`-only, zero-rust-bitcoin-dep posture" and is "the heaviest external dependency; strains the sovereign zero-dep posture." **This is the sharpest technical tension the new PRD must resolve**: either justify accepting the dependency (and update the "zero-dep posture" framing estate-wide, since it's referenced as an existing architectural commitment, not just this ADR's opinion), or explain how sidestr's RGB integration avoids pulling `rgb-core`/AluVM into the same crate graph that currently excludes it.

3. **Licence tension — NOT currently asserted in canon, must be newly established.** A targeted search for "AGPL" across the whole corpus returns **only unrelated hits** (general licence-consolidation ADRs — ADR-016, ADR-2030, `docs/developer/licensing.md`, `VisionFlow/docs/architecture/licensing.md` — none of which mention sidestr, RGB, or `bitcoin-desktop`/JSS AGPL provenance). **There is currently zero canon record of a sidestr/JSS-AGPL-3.0 vs. Apache-2.0-crates licence conflict.** The team-lead's framing ("AGPL-3.0 sidestr/JSS vs Apache-2.0 crates") is **not yet grounded in this estate's documents** — it must be a fresh finding the new PRD introduces, checked against `ADR-2030-permissive-licensing-for-publishable-service-crates.md` (which sets the estate's *forward* policy: publishable service crates must be permissively licensed) and `agentbox/docs/developer/licensing.md`. Given ADR-2030's existing standing rule (crates intended for crates.io publication get permissive licences; the operator's stated rule per line 25 of that ADR restricts non-permissive dependencies to specific module classes), **a sidestr/JSS AGPL dependency pulled into any crate on a path to crates.io publication is very likely a direct policy violation** and should be flagged as a blocking constraint, not a footnote, in the new PRD.

4. **"No native EVM/USDC rail" (PRD-015 v1.2, C11, formally rejected) vs. any RGB/sidestr tooling with EVM-adjacent dependencies.** If the "sidestr" substrate under evaluation has any EVM-chain compatibility layer, bridge, or wrapped-asset concept, it collides directly with this explicit, dated (2026-06-12), operator-signed rejection. Silence on this point in the new PRD would be a gap; explicit reconciliation (confirm still Bitcoin/Lightning-only, or record a superseding decision) is required.

5. **Escrow named in the ontology, absent in code, TOCTOU-flagged as a known custody risk (ADR-124 R6).** Any RGB/DLC feature that implies escrow-like locking (which single-use-seal-based settlement typically does) is filling a documented gap that already carries an open remediation requirement (per-ledger advisory lock/CAS, atomic record-if-absent) — the PRD should treat closing R6 as a **precondition**, not a parallel nice-to-have, since the new work will likely be the first thing to actually exercise escrow-shaped code paths at real stakes.

6. **Regulatory non-exemption claim (T1-7/T8-1) vs. a common marketing framing of RGB as "regulation-avoiding via trustlessness."** Canon is explicit and repeated: **removing operator custody does not remove any of the three named UK legal obligations at any trust level.** If the new substrate's business case leans on regulatory avoidance via RGB's client-side-validation model, that framing directly contradicts this standing canon position and must be argued against explicitly, not assumed away.

7. **"Single-use *anchor*" vs. "single-use *seal*" — a precise terminology trap.** ADR-124 §2.3 is unusually blunt: *"Do not call the current substrate a 'single-use seal' in code, docs, or marketing until that [spent-exactly-once] check exists."* Any RGB-related document (including the sidestr PRD itself) that casually calls the existing MRC20/block-trail anchor chain a "single-use seal" before the seal-closing-witness check (T1-5) lands would repeat a terminology error this ADR went out of its way to forbid.

8. **Federation economics is nearly a blank slate (Theme 7), so there is little to contradict there** — treat this as an opportunity, not a tension: the PRD can define federation-crossing rules for RGB assets without displacing an existing decision, only needs to be consistent with the one existing precedent (receipt-stays-local / activity-and-bead-cross split in economy-loop.md, T7-2).

## Summary (for team-lead)

- **Theme 1 (RGB/DLC/CSV ladder):** 8 assertions, all from two tightly-linked ADRs (ADR-124, ADR-128). Core finding: RGB is canon's explicitly deferred, optional, last rung (L3) — the sharpest re-sequencing decision the new PRD must own.
- **Theme 2 (gitmark/blocktrails):** 5 assertions. Core finding: a "no parallel design, adopt Carvalho verbatim" precedent already exists (ADR-128) that the new work should either follow or explicitly deviate from.
- **Theme 3 (402/pod trust ledger):** 5 assertions, frozen fixture-tested grammar (ADR-032) + live WebLedger fail-closed design. Core finding: adding an RGB-payable scheme is an ADR-032-revision-plus-fixtures event, not a free extension.
- **Theme 4 (Lightning/zaps/NWC):** 6 assertions. Core finding: Lightning-via-NWC-on-own-node is the sole planned real-money rail (Phase 3, not yet live); zaps are wholly absent from canon; x402/EVM rail formally rejected.
- **Theme 5 (agent wallets/budgets):** 5 assertions. Core finding: canon has no "agent wallet" object — only a policy-gated per-DID Web Ledger balance plus deterministic spend-policy middleware; non-custodial-by-default is a named design stance.
- **Theme 6 (tokens/assets/webledgers):** 5 assertions. Core finding: MRC20 + live AMM/order-book already exist as the token/asset rail; escrow is ontology-named but explicitly unbuilt and TOCTOU-flagged; the custody-disablement flag is a named-but-unbuilt containment mechanism.
- **Theme 7 (federation economics):** 3 assertions. Core finding: PRD-010 (the federation PRD) has zero economic content; BC20 receipt-crossing is explicitly incomplete — largely greenfield.
- **Theme 8 (regulatory containment):** 3 assertions. Core finding: a detailed, cited UK regulatory matrix already exists and asserts RGB/trustlessness does **not** exempt any level from any of three legal-product-class obligations; testnet-pin + on-seal-immutable-flags is the one concrete containment mechanism on file (unbuilt).

**Top 5 tensions:**
1. RGB explicitly sequenced last/optional/audit-gated in ADR-124/128 — the new PRD must formally re-sequence, not silently override.
2. `rgb-core`/AluVM directly conflicts with the stated `k256`-only zero-Bitcoin-dep posture — the single sharpest dependency-level tension in canon.
3. No AGPL/licence conflict is currently documented anywhere in canon — the sidestr-AGPL-vs-Apache tension is a **new finding the PRD must establish**, and should be checked hard against ADR-2030's forward permissive-licensing policy for publishable crates.
4. "Removing custody does not remove regulatory obligation" is asserted flatly and repeatedly — contradicts any RGB-as-regulatory-escape framing.
5. "Single-use seal" is a reserved term canon says must not be used until a specific unbuilt check exists — a live terminology trap for any RGB document.
