# Validate the skill without inventing improvement

Structural checks establish packaging quality. Public example execution
establishes those examples. An independent forward test establishes what that
participant did on its task. Measured improvement requires a separate, controlled
comparison. None substitutes for the others.

## Structural audit

Check the entrypoint's portable frontmatter, name/directory parity, concise
trigger description, progressive references, relative-link closure and complete
licence/provenance records. Both target harnesses should discover the same
canonical payload. Inspect migrated callers and the installed layout; the hard
cutover must leave no active old skill or implementation.

Check every declared runtime feature against a shipped implementation, every
command example against the current executable, and every numeric result
against retained evidence. Logical responsibilities must not be presented as
spawned agents. Configuration without a loader must not be advertised as
enforcement. Missing optional tools remain visible limitations.

## Public behaviour cases

These are acceptance cases for authors and reviewers; they are not held-out
material and must not be reported as such.

| Case | Useful observation |
|---|---|
| A test fails during fixture construction before the claimed replay check | Records setup/observation failure, repairs the fixture and reaches the intended assertion with a supported control |
| A producer fix exists but the consumer lockfile pins an older release | Reports the actual consumed version and keeps source repair separate from adoption |
| Required auditor is unavailable; a same-family advisor responds | Retains advice and unmet independence without fabricating a pass |
| Reviewer exits with a stale comment and no valid fresh export | Preserves incomplete/error state rather than inventing an empty clean review |
| A two-line ordinary change needs a local regression | Avoids an unnecessary workshop, fleet, paid review or tracking database |
| A genuine offline text-only implementation task has no runtime | Substitutes concrete values through the visible contract and reports static limits without executed-test claims |
| A hardware/user observation is required | Separates simulated/partial/manual observation and actual acceptance authority |
| Two similar validators have different credential lifetimes | Compares contracts/callers and retains intentional differences |
| Rejected content remains reachable by known identifier | Checks publication stores/readers and migration rather than only hiding search results |
| A new registry release exists after local path-patched tests | Exercises the real consumer pin before claiming adoption |

## Independent forward test

Give a separate participant a realistic request, this candidate skill and the
minimum raw project material. Do not provide the suspected defect, intended
answer, planned fix or earlier conclusions. Use an isolated owned checkout and
restrict side effects to the evaluation's authorised scope. Keep its actual
trajectory, artefacts, commands and any inability to execute.

Grade whether the participant reached the relevant behaviour with a valid
control, respected subject/version and authority boundaries, avoided false
closure and completed the requested task proportionately. Do not grade mere
presence of headings or quoted skill vocabulary. A refusal-only strategy must
fail the supported control. Changes to the skill should address demonstrated
mistakes rather than accumulating universal rules for every hypothetical risk.

A coordinator owns this pass and reports whether it ran. This file is a
procedure and public oracle; it contains no claim that forward testing passed.

## Measured tuning

Freeze the baseline skill, candidate, task set, evaluator and budgets before
comparison. A curator independent of implementation should create sealed
held-out cases with different fixtures and withhold their answers. If a case
is shown during debugging, move it into regression material and replace it in
the held-out set.

Use paired conditions with the same task/tool access and record actual model
identities, order and resource budgets. Replicate enough to observe variability;
the initial programme calls for at least three trials per item. Keep training,
validation and final test separate. Do not leak another arm's outcome or the
reference solution into optimisation prompts.

Report per-item outcomes, denominators, uncertainty, cost and failures alongside
any aggregate score. Structural compliance or a successful public example does
not demonstrate empirical uplift. No such uplift is claimed by this package.
